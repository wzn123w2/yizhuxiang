# 山寺 · 静静坐一会儿（本地重建版）

参照 [sansatemple](https://sansatemple.com) 的玩法结构，在浏览器里重建的一间三维佛堂。
纯前端、无后端、无外部美术/音频资源 —— 场景和声音全部用代码生成。

**这一版是"骨架"，目标是先把山寺的操作手感对齐，然后我们一起慢慢改。**

---

## 跑起来

```bash
cd shanshi
npm install
npm run dev -- --host
```

- 电脑：`http://localhost:5173/`
- 手机：用终端打印的 `Network` 地址（同一 WiFi）

生产构建：`npm run build && npm run preview -- --host`

## 部署上线

部署形态是**一个 Node 进程**：同一端口既托管 `dist/` 静态页，也接 `/ws` 同修连线。
前端用 `location.host` 拼 ws 地址，所以换域名、上 HTTPS 都不用改代码。

```bash
npm ci && npm run build
PORT=8787 MAX_PLAYERS=12 node server/index.mjs
# 打开 http://<IP>:8787/ 就是完整应用；健康检查 /healthz
```

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | 8787 | 监听端口，平台注入的 `PORT` 可直接用 |
| `MAX_PLAYERS` | 12 | 一间法堂上限，与殿内 12 张坐垫对应 |

`deploy/` 里现成的模板：

- `deploy/Caddyfile` —— 反向代理 + 自动 HTTPS（**最省事，自动透传 WebSocket**）
- `deploy/nginx.conf` —— nginx 版，手写了 Upgrade 头与 90s read timeout
- `deploy/shanshi.service` —— systemd 守护（路径/用户按机器改）
- `Dockerfile` —— 多阶段构建，`docker build -t shansi . && docker run -p 8787:8787 shansi`

注意事项：

- **只能单实例**：玩家与坐垫状态都在内存里（`server/index.mjs` 的 `players` / `seats`），不能横向扩容、不能部署到 serverless
- 服务端每 20s 发一次 ping，反向代理的 `read_timeout` 必须大于这个值
- 想在国内托管需域名备案；先用 `http://<IP>:8787` 明文试玩也可以（微信内置浏览器能开）

## 场景结构

```
        z=-10  ┌─────────────┐  佛殿后墙
               │   佛坛 · 佛像  │
               │   12 张坐垫   │  ← 殿内（地面 y=0）
        z=+10  └──┬───────┬──┘  敞开的前廊
                  │ 三级台阶 │     y: 0 → -0.9
        z=+12.7 ┌─┴───────┴─┐
               │  石板路     │
               │  假山 · 水池 │  ← 庭院（地面 y=-0.9）
               │  松树 · 石灯 │
        z=+34   └── 月洞门 ──┘
```

人可以从殿内直接走下台阶进庭院，再走回来；`walkRects` 把"殿内 / 台阶 / 庭院"三块拼成连通的可行走区域，
墙面用轴分离滑动处理（贴着墙走不会卡住），假山、树、香炉、石灯是圆形障碍推开。

### 镜头不穿屋顶

第三人称镜头在殿内容易翻到屋檐外面，被屋顶整个挡住。这里两层处理：

1. **高度钳制**：进了殿（`z < 10.6` 且在墙内），把机位压到天花板下 0.45m，
   并且保持到角色的距离不变、只缩短水平分量 —— 出来的是"更低更平"的宽景，
   而不是顶到天花板下垂直俯视。进出殿用插值过渡，不会跳。
2. **射线碰撞**：从注视点往理想机位打一条 `Raycaster`，撞到墙/屋顶/天花板就把
   相机收到撞点前 0.4m。这条兜底，别的角度、别的场景都能用。

"是否在殿内"是在 `main.ts` 的帧循环里算的，`controls.maxCamY` 由外部控制；
`temple.occluders` 是登记好的遮挡构件（后墙/侧墙/两片屋面/正脊/檐口/天花板）。

## 代码结构

```

├─ world/
│  ├─ textures.ts   程序生成纹理（石板、木纹、墙面、光晕、烟雾）
│  ├─ temple.ts     ★ 大殿：佛坛、佛像、柱、灯笼、坐垫、香炉、木鱼台、钟、
│  │                  香火粒子、昼夜灯光
│  └─ monk.ts       ★ 小沙弥：纯几何体拼装 + 姿态目标值插值
├─ game/
│  └─ controls.ts   ★ 环绕相机 + 点地/摇杆/WASD/滚轮/捏合
├─ audio/
│  ├─ engine.ts     AudioHost：唯一 AudioContext 持有者，三条总线，负责解锁与重建
│  └─ sounds.ts     木鱼 / 念珠 / 磬 / 合掌 / 上香 / 山风 / 唱诵（全部现场合成）
├─ ui/
│  └─ beads.ts      念珠横向珠串（浮点位置 + 缓动 + 过珠判定 + 自动捻珠）
├─ core/save.ts     本地存档
└─ main.ts          流程编排与交互状态机
```

### 两个关键设计

**1. 角色动画是"目标值 + 插值"，没有动画剪辑**

`Monk.setPose()` 只改一组目标角度（躯干前倾、手臂旋转、缩放），
`update()` 每帧朝目标插值。好处是切换姿态天然带过渡、不用做动画状态机，
坏处是做不了复杂的动作——够用，且改起来极快。

**2. 音源模块不缓存 AudioContext**

iOS / 微信内置浏览器切后台会销毁上下文，回来必须重建。
所以 `AudioHost` 独占生命周期，`Wind` / `Chant` 通过 `host.onRebuild()` 重新挂载。
`rebuild()` 里回调放在 `await unlock()` **之后**，否则新上下文还没 running，音源静默失败。

## 已知问题

- 从正后方看，小沙弥的"耳朵"曾经像眼睛（已缩小并内收，进一步可只留一侧轮廓）
- 灯光在低端机上可能需要降级（阴影贴图 2048，殿内 8 个点光源）
- 夜间亮度是按"能看清路、但仍是夜"调的；如果觉得还想更亮，改 `temple.ts` 的 `NIGHT.ambI` / `NIGHT.hemiI`
- 首屏要等 `renderer.compile()`，低端机会有 1-3 秒白屏，应该加真实进度反馈

- `main.ts` 末尾留了一个调试钩子 `window.__ss()`，正式版删掉
